# 各板块精修历史核对与恢复（0.12.8）

本次按板块的用户要求、实际修改补丁、后续交叉修改和界面交付记录核对；不把文件修改时间或整包版本号当作精修是否保留的依据。

## 查到了什么

核对了 11 个相关对话，整理出 316 份补丁记录、164 条可能写入文件的命令记录，以及对应用户消息和交付说明。原始记录提取在 `build/history-audit/`，只用于追溯，没有重新执行历史命令。时间均按北京时间理解。

Git 的上一个项目提交停在 10 月 13 日，10 月 27–28 日各轮精修没有分别提交，因此 Git 本身无法给出每次精修的完整快照。0.12.7 的提交只是把当时主目录封存起来，不能单凭它证明各精修目标全部兼容。

确实发现了一个会改变用户体验的交叉修改：

1. “重新设计简洁且突出重点的板块样板图”（执行与 AI 聊天）在 10 月 28 日 09:28 收到明确要求：首屏直接问“买什么”，下方为购物原则；输入后才进入快速决策／研究模式。
2. 该功能已经实现并交付，随后又完成了聊天气泡、Markdown、多轮记录等精修。
3. “评审 C++ 桌面版界面与交互简洁性”（购买流程）约 11:00 的写入命令，直接用字符串区间替换了 `ExecutionWidget.cpp` 的输入卡片，把输入框和下一步改成“我现在想买……”按钮，并把名称输入移到了后面的简报页。证据：`build/history-audit/commands/0155-purchase-flow.txt`。
4. 购买流程的统一因此覆盖了执行首屏已经精修好的渐进引导。其余决策和聊天代码仍在，整包测试也可以通过，但用户实际走的入口已经不同。

## 本次恢复

执行首屏恢复直接输入商品名称和“生成决策简报”。回车或点击后直接进入原来的快速／研究选择，不需要先在购买弹窗中绕一圈。金额、用途、分类继续按需补充，点击开始才创建会话。

共同的文字／截图购买弹窗保留为轻量次级入口，并带入已经填写的商品名。主页原来的三步购买流程、截图解析、研究交接、资料流转、购买记账和复盘安排继续使用已实现的逻辑。简报页修改商品名称与首屏同步；返回或取消弹窗保留输入。

## 为什么上一轮测试没有发现

旧的执行 UI 测试通过内部 `prepareDecision()` 直接进入简报，绕过了用户实际看见的首屏。它能验证后面的预算、计时、AI 和购买数据，却没有保护“首屏必须能直接输入”这条精修要求。

新增 `focusedInputSurvivesPurchaseFlowAndKeepsSharedEntry`，先在 0.12.7 上复现输入框不可见，再验证恢复后的直接输入、回车进入模式、编辑与返回、共同弹窗带入草稿，以及这些步骤不产生消费或决策会话。既有执行测试也改为走可见的下一步按钮或回车。

最终验证结果见 0.12.8 运行包内的 `build-manifest.json` 和 `verified-tests.log`；同一次完整测试生成的页面截图位于 `build/preview/history-verified/`，用于检查各板块来自同一份源码。
